# 월간 브리핑 카카오 알림톡 발송 설계

> "부서로 그냥 보낼 수 없다" — 알림톡의 근본 제약을 설계에 반영한다.
> 알림톡은 **개별 사람(전화번호)** 에게만 가고, "부서/팀"이라는 추상 대상엔 발송 불가.

---

## 0. 핵심 원칙 — 조직이 아니라 "사람"에게 보낸다

- 알림톡 발송 단위 = **개인 전화번호**(카카오톡 가입번호로 매칭). 채널 친구/UUID/부서명으로 못 보냄.
- 따라서: 각 조직단위의 **책임자를 실명·전화번호로 등록** → 그 개인에게 자기 조직 스코프 브리핑을 보낸다.
- ❌ "인천영업부로 보낸다"  →  ✅ "인천영업부장 **홍길동(010-xxxx-xxxx)** 에게 인천영업부 현황을 보낸다"
- 한 조직에 수신자가 여러 명일 수 있고(정·부책임자), 한 사람이 여러 조직을 겸임할 수도 있음 → 디렉터리에서 명시.

---

## 1. 수신자 디렉터리 — 최우선 선결과제 (이게 없으면 발송 불가)

**스키마** (`recipients.json` 의 `users`, S3 암호화·접근제한 보관):
```
"users": {
  "<id>": {
    "name": "홍길동",
    "phone": "01012345678",           // 알림톡 매칭 키 (하이픈 없이)
    "role": "영업부장",
    "부문": "수도권", "영업부": "인천영업부", "팀": null, "매장": null,
    "consent": true,                   // 수신 동의/근거 확보 여부
    "consent_at": "2026-07-01",
    "active": true                     // 퇴사·보직변경 시 false
  }
}
```

**개인정보·수신근거 (반드시 처리):**
- 정보성 알림톡(사내 안전보건 브리핑)은 광고 아님 → 별도 *광고* 수신동의는 불요. 단 **업무 관련 정보 수신 안내 + 수신거부 수단**은 제공(최초 발송 시 안내, 수신거부 시 `active=false`).
- 전화번호는 **최소수집·암호화 보관**(S3 SSE + IAM 최소권한), 목적 외 사용 금지, 보직변경/퇴사 시 갱신·삭제.
- 명단 확보 경로: (a) 관리자 UI 수기 등록 (b) 인사/조직도 시스템 연동 (c) 최초 1회 각 책임자 동의 수집.

**현재 상태**: `recipients.seed.json` 의 mock 6명(전화 010-0000-000X)뿐 → **실명단 확보가 실발송의 1차 관문.**

---

## 2. 발송 경로 — 어떻게 나가는가

카카오는 알림톡 API를 일반에 직접 열지 않는다. **카카오 인증 비즈메시지 대행사(중계사)** 를 통해서만 발송.

```
[매월 1일 06:00 KST]
 EventBridge → briefing Lambda
   ├─ org_rollup + kpi_targets 로 각 수신자 스코프 브리핑 변수 산출
   ├─ users 디렉터리에서 (전화번호 + consent=true + active) 필터
   └─ 대행사 REST API 호출:
        POST {대행사}/alimtalk/send
        { senderKey: <발신프로필키>,
          templateId: <승인템플릿ID>,
          messages: [ { to: "01012345678",
                        variables: { 조직명, 기간, 건수, 목표대비, 전년대비, 핵심유형 },
                        buttons: [{ name:"우리 조직 현황 보기", linkMo:<딥링크>, linkPc:<딥링크> }],
                        fallback: { type:"SMS", text:"..." } } ] }
       → 카카오 → 수신자 카카오톡
```

**구성요소 (사용자 준비):**
| 요소 | 설명 | 확보 주체 |
|---|---|---|
| 카카오 비즈니스 채널 | 다이소 공식 채널 | 사용자(있으면 재사용) |
| 발신프로필(sender key) | 채널 인증 후 발급 | 사용자 |
| 승인 템플릿(template ID) | 검수 2~3영업일 통과 | 사용자(문안=아래 3장) |
| 대행사 계정 | 발송 중계 + API 키 | 사용자 선택 |

**대행사 후보** (하나 선택 또는 기존 계약사): 솔라피(Solapi)·비즈뿌리오·NHN Cloud(Toast) Bizmessage·센드온·알리고 등. 선택 기준 = **① 건당 단가 ② REST API 편의 ③ SMS 대체발송 지원 ④ 안정성/실패 리포트**.

**대체발송(fallback)**: 수신자가 카카오톡 미가입·채널차단이면 알림톡 미도달 → **SMS/LMS로 자동 대체발송**(대행사 기능). 브리핑 요약 텍스트 + 링크로 보냄.

## 3. 템플릿 설계 — 어떤 것을 쓰는가

**유형: 강조표기형**(제목 강조 + 본문 + 버튼) — 조직명·기간을 제목에 강조해 한눈에.

**템플릿 (검수 제출용):**
```
[강조 제목]  #{조직명} · #{기간} 안전 브리핑
[강조 보조]  사고 #{건수}건 · 목표 #{목표대비}

안녕하세요, #{조직명} 안전현황을 전해드립니다.

▶ #{기간} 발생: #{건수}건 (목표 대비 #{목표대비})
▶ 전년 동월 대비: #{전년대비}
▶ 최다 재해유형: #{핵심유형}

상세 현황·예방 조치는 아래 버튼에서 확인하세요.
```
- 버튼: `우리 조직 현황 보기` (웹링크 → 대시보드 조직 딥링크 `#tab=dept&scope=조직명`)
- 하단 고정: `※ 본 메시지는 안전보건 업무 안내입니다. 수신거부: (수단)`

**검수 통과 요령**: 광고·프로모션 표현 금지, 변수는 값이 비어도 문장이 성립하게, 이모지 남용 금지("▶/▲/▼"는 허용), 정보성 목적 명확히. **반려 시 사유 반영 재제출**.

**1종 vs 분화**: `#{조직명}` 변수 하나로 부문/영업부/팀/매장 전 레벨 커버 가능 → **우선 1종으로 승인**받고, 부문장용(요약형)·현장용(상세형) 분화는 운영 후 필요 시.

---

## 4. 코드 반영 (설계 → 구현 갭)

- **현행 문제**: `KakaoNotifier`(예방카드)는 **친구에게 메시지 API(UUID)** 이고, `send_alimtalk` 도 `receiver_uuids` 를 받음 → **알림톡은 전화번호 기반이라 부적합**.
- **수정 방향**:
  - 예방카드(친구톡·UUID) 와 브리핑(알림톡·전화번호·대행사) = **별도 발송 경로**로 분리.
  - `send_alimtalk(recipients_phone, template_id, variables, buttons, fallback)` — 대행사 REST 클라이언트로 구현(대행사 확정 후 API 규격 반영).
  - 수신자는 `users` 의 `phone`(consent·active 필터) 사용.

## 5. 확정된 방향 (2026-07 사용자 결정)

- **수신자 = 인사/조직도 시스템 연동** (수기 아님). HR의 사람 레코드에서 직책·연락처·소속을 가져와 자동 구성.
- **카카오 발송 = 기존 보유/계약** (신규 구축 불요). 발신프로필키·템플릿ID·대행사 API키만 주입.

### 5-A. HR → 수신자 매핑 (핵심 설계)

HR 시스템엔 "사람 + 직책 + 소속"이 있지, "브리핑 스코프"는 없다. **직책 → 스코프 레벨**로 매핑한다:

| HR 직책(키워드) | 스코프 level | 스코프 key(=소속) | 예 |
|---|---|---|---|
| 영업부문장 / 부문장 | `bumun` | 소속 부문 | 수도권영업부문장 → 수도권 |
| 영업부장 / (영업)부장 | `dept` | 소속 영업부 | 인천영업부장 → 인천영업부 |
| 팀장 | `team` | 소속 팀 | 일산팀장 → 일산팀 |
| 점장 / 점포장 | `store` | 소속 매장 | 고양화정점장 → 고양화정점 |

**정합성 관문**: HR의 소속 명칭이 `org_rollup.json` 키(인천영업부·일산팀·고양화정점)와 **정확히 일치**해야 브리핑 데이터가 붙는다. 불일치 시 **별칭 매핑표(org_alias)** 로 보정(예: HR "인천영업부문" ↔ 사고DB "인천영업부"). → `core/hr_sync.py` 가 담당.

**연동 방식(택1, 사용자 확인 필요)**: (a) HR REST API 주기 pull (b) HR CSV/엑셀 정기 export → S3 → 파싱. 어느 쪽이든 `hr_records_to_users()` 로 `users` 디렉터리 생성.

**개인정보**: 전화번호는 연동 시점에만 가져와 암호화 보관, 목적 외 미사용, 퇴사·보직변경은 HR 상태를 그대로 반영(active).

### 5-B. 대행사 어댑터 (기존 계약사)

`send_alimtalk` 을 **전화번호 기반 + 대행사 어댑터**로 재구현. 대행사별 API가 달라 어댑터로 격리:
- `AlimtalkSender` 인터페이스: `send(template_id, sender_key, messages[{to, variables, buttons, fallback}])`.
- 벤더 구현체(솔라피/비즈뿌리오/NHN 등)는 확정 후 1개만 작성. 그 전까진 mock.

### 5-C. 남은 확인 2가지 (구현 착수 트리거)
1. **대행사 이름** — 어느 곳인가?(솔라피/비즈뿌리오/NHN Toast/센드온/알리고/기타) → 해당 REST API로 어댑터 1종 작성.
2. **HR 연동 방식** — REST API 인가 정기 export 인가? 사람 레코드 필드(직책·연락처·소속 컬럼명)는? → `hr_records_to_users` 입력 스키마 확정.

이 2가지가 오면: 템플릿 검수 제출 → 승인 후 어댑터 완성 → `ALIMTALK_SENDER_KEY`·`ALIMTALK_TEMPLATE_BRIEFING`·대행사키 주입 → `NOTIFY_CHANNEL=kakao` 실발송.
