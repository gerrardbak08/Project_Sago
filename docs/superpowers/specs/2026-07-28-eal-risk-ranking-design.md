# 연간 기대손실(EAL) 기반 리스크 정량화 — 설계 문서

**작성일**: 2026-07-28
**수정일**: 2026-07-29 (§9.2 사망 처리 결정, §5·§6·§7·§8 반영)
**상태**: 설계 승인됨 (구현 전)
**출처**: PRISM(원자력 확률론적 안전성 평가) 기법 검토 결과 중 SAGO 적용 가능분

---

## 1. 개요

사고 리스크를 **연간 기대손실(EAL, Expected Annual Loss) 금액**으로 환산해, 현재 추상적 지표(위험점수·평균 휴업일수)로 표현되던 우선순위를 재무 언어로 바꾼다.

PRISM의 핵심 산식 `EAL = Pf × L`을 차용하되, PRISM이 데이터 부재로 공학 모델을 써서 추정하는 `Pf`를 **우리는 실측 620건으로 직접 산출**한다. 모델 가정이 개입하지 않아 방어 가능성이 높다.

### 해결하는 문제

현재 요인×결과 탭의 '고위험 조합'은 **평균 휴업일수만으로 정렬**되어 있어, 표본 5건짜리 조합이 실제 손실 기여 1위 조합보다 위에 표시된다.

| | 현재 정렬 (심각도만) | 개선 후 (EAL) |
|---|---|---|
| 1위 | 넘어짐 @ 사다리 위 — 165일 (5건) | 넘어짐 @ 계단 (87건 · 평균 91일) |
| 실질 | 총 기여 약 825일 | 총 기여 약 7,900일 |

## 2. 범위

### 포함

1. **리스크 랭킹 재정렬** — 빈도×심각도(=EAL) 기준
2. **EAL 4개 집계 축** — 유형×장소 / 조직 계층 / 매장별 / 전사 총액
3. **사망 재해 분리 축** — 금액(EAL)에서 제외하고 건수 + 법정 요양근로손실일수로 별도 표기 (§9.2 결정)

### 제외 (YAGNI)

- **생애주기 누적손실(ELL), 보험료 환산 `×(1+a+b)`, 요율 시뮬레이션** — PRISM엔 있으나 산재보험은 법정 요율제라 협상 대상이 아니고, 개별실적요율은 별도 법정 산식이라 이 프레임으로 계산하면 **틀린 숫자**가 된다.
- **Event Tree(방벽 기반 예방 설계)** — 별도 설계로 분리. 사유는 §10 참조.
- **공상비용(`cost`) 반영** — 620건 중 실측 16건뿐이라 표본 노이즈가 지배하고, 근로손실일수와 성격이 겹쳐 이중계상 위험.
- **강도율(비율) 산출** — 법정 산식 `강도율 = 총요양근로손실일수 ÷ 연근로시간수 × 1,000`의 **분모인 연근로시간수가 데이터에 없다**(근로자수 10,692명은 있으나 시간 데이터 없음, 기존 구현도 없음). 시간을 가정해 넣으면 Pf를 실측으로 잡은 §3.1 원칙과 어긋나므로, v1은 **분자(요양근로손실일수)만** 표기하고 비율은 근로시간 데이터 확보 후로 미룬다.

## 3. 핵심 산식

### 3.1 기본형

```
EAL(그룹 c) = λ_c × L̄_c

  λ_c = n_c / T     연간 발생빈도 (건/년)
  L̄_c = 건당 평균 손실액 (원)
```

### 3.2 모수 — 영업부문 기준

모든 EAL은 **영업부문(수도권+지방) 620건** 기준으로 통일한다. 기존 `location`·`subCause` 집계가 이미 이 모수(`sales`)를 쓰므로, 여기만 전체(646건)로 하면 같은 화면 안에서 숫자가 어긋난다. 기타부문 26건은 제외되며 카드 라벨에 **'영업부문 기준'**을 명시한다.

### 3.3 관측 기간 T

`year`/`month` 필드 기준 **최초 월 ~ 마지막 완료 월**. 진행 중인 당월은 **분자·분모 양쪽에서 제외**한다 — 미완료 월을 온전한 1개월로 세면 빈도가 과소 추정되고, 안전 지표에서 위험을 낮게 잡는 건 위험한 방향의 오차다.

현재 데이터 기준:

| 항목 | 값 |
|---|---|
| 관측 범위 | 2024-01 ~ 2026-07 (31개월) |
| 완료 월 | 2024-01 ~ 2026-06 = **30개월 = 2.5년** |
| 완료월 내 사고 | **609건** (당월 2026-07의 11건 제외) |

### 3.4 레코드 단위 배분 (가법성 보장)

그룹별로 평균을 내서 곱하면 **축이 바뀔 때 합계가 어긋난다**(전사 총액 ≠ 유형별 합계). 대신 사고 1건마다 연간 기여분을 계산해두면 어떤 축으로 묶든 단순 합산이라 항상 정합한다.

```
1) 결측 보정
   effLossDays_i = loss_days_i > 0 ? loss_days_i : typeMean[type_i]

2) 사고 1건의 연간 기대손실 기여분
   eal_i = effLossDays_i × dayRate(year_i) / T

3) 어떤 집계든 합산
   EAL(그룹) = Σ eal_i
```

결측 보정을 **재해유형 기준**으로 하는 이유: 손실 규모가 장소보다 유형에 크게 좌우되고(질병 123일 vs 끼임 32일), 유형별 표본이 집계에 충분하다.

**모수에서 사망 제외** — `isFatal(rec)`인 레코드는 위 1~3단계 전체에서 빠진다(`typeMean` 산출 시에도 제외). 사유와 별도 표기 방식은 §9.2 참조.

### 3.5 손실 단가 dayRate

```
dayRate(y) = DAILY_VALUE_PER_WORKER ?? ( 일급(y) × (1 + INDIRECT_COST_MULTIPLIER) )
                                          └ 하인리히 1:4 (현행 임시 모델)
```

`CostRisk.jsx`의 기존 로직과 **동일한 값**을 써야 한다. 현재 그 로직이 컴포넌트 내부에 있어, 이대로 두면 두 화면이 서로 다른 금액을 말하게 된다. → `dayRate`를 `eal.js`로 추출하고 `CostRisk.jsx`가 import하도록 변경한다(§7).

`DAILY_VALUE_PER_WORKER`에 실제 값이 들어오면 **재베이크 없이 전 화면 자동 전환**된다.

### 3.6 매장별 — 신뢰도 가중 (Bühlmann)

매장 1,343개 중 대부분이 사고 0건이라, 실측 빈도를 그대로 쓰면 87%가 "연간 기대손실 0원"이 되어 *"과거에 없었으니 앞으로도 없다"*는 잘못된 신호를 준다. 보험 통계의 표준 해법인 신뢰도 가중을 적용한다.

```
Z_s = n_s / (n_s + k)                       k = 3 (기본값)
λ_s = Z_s × (n_s / T) + (1 − Z_s) × λ_peer
```

- `k`는 `storeEal(records, stores, { k = 3 })` 옵션으로 주입한다. 모듈 내 하드코딩 금지 — 검증 스크립트가 `k` 변화에 따른 단조성을 확인해야 하기 때문.
- `λ_peer` = **같은 평수 버킷** 매장들의 매장당 평균 빈도. 버킷은 `storesData.js`(`MAP_STORES`)의 `ar`(평수) 필드를 기존 `parseHelpers.sizeBucket()`으로 분류해 사용한다(소형 ~100평 / 중형 100-250 / 대형 250-400 / 특대 400+).
- 사고 4건 매장 → 자기 실적 57% 반영 / 0건 매장 → 동료집단 평균으로 수렴

**성질**: `storeEal`만 peer 평균과 혼합되므로 **매장별 EAL 합계는 전사 총액과 일치하지 않는다.** 0건 매장에 위험을 나눠주고 다발 매장에서 덜어내는 것이 이 기법의 목적이므로 의도된 동작이다. 나머지 세 축(전사·조직·유형×장소)은 완전 정합한다.

## 4. 모듈 구조

### `src/utils/eal.js` (신규)

React·데이터 import가 없는 **순수 함수 모듈**. 의존은 `constants/metrics.js` 하나뿐이라 단위 검증이 쉽다.

```js
export function dayRate(year)                    // 손실 단가 (CostRisk와 공유)
export function observationPeriod(accidents)     // → { years, months, firstYm, lastCompleteYm }
export function withEal(accidents, period)       // → 각 레코드에 eal_i 부착
export function sumEal(records, groupBy)         // → [{ key, n, lambda, avgLossDays, eal }]
export function storeEal(records, stores, opts)  // → 신뢰도 가중 매장별 (별도 경로)
```

호출부:

```js
const period  = useMemo(() => observationPeriod(D.accidents), [D.accidents]);
const records = useMemo(() => withEal(scoped, period), [scoped, period]);
const byLoc   = useMemo(() => sumEal(records, a => `${a.typeCanon}|${a.locLabel}`), [records]);
```

### 계산 위치를 런타임으로 택한 이유

빌드타임(`processAccidents.js` 통합) 대신 런타임 유틸을 택했다.

1. 곧 들어올 인당 생산성 실제 값이 **재베이크 없이 즉시 반영**된다
2. 연도 필터·기준 토글(사고경위↔산재승인)에 자동 반응한다
3. `CostRisk.jsx`가 이미 런타임 단가 계산 패턴이라, 로직을 공유해 **두 화면 숫자가 어긋나지 않는다**
4. 620건 계산은 성능상 무시할 수준

## 5. 화면 반영

`StoreRiskMap.jsx`(1,694줄)는 **손대지 않는다** — 매장별 EAL은 지도 드로어 대신 자체 랭킹 리스트로 처리해 회귀 위험을 줄인다.

### ① 요인×결과 탭 (`CrossAnalysis.jsx`) — 정렬 교체

기존 '발생 장소 분석' 카드 내 '고위험 조합' 섹션에서 **정렬 기준만** 평균 휴업일수 → EAL 금액으로 교체. 표시에 연간 기대손실을 추가하고, 표본 5건 미만 필터는 유지.

### ② 비용 손실 탭 (`CostRisk.jsx`) — EAL 카드 신설

- 상단 KPI에 `연간 기대손실(EAL)` 추가 — 기존 '총 추정 재무손실'과 형제 배치
- 그 옆에 **금액 없는 `중대재해` 타일** (`LegalReporting` T10 타일과 같은 어휘·색 `#D70011`). 클릭 시 `setTab('legal')`

  ```
  중대재해
  1 건 · 법정 요양근로손실일수 7,500일
  금액 환산 대상 아님 · 법적 보고 탭에서 관리
  ```

  이 타일이 "사망을 무시한다"는 인상을 막는 핵심 장치다. 사망은 사라지는 게 아니라 같은 줄에 **자기 단위(건·일)로** 남는다.
- **연간 기대손실 상위 매장 Top 20** 리스트 (신뢰도 가중 적용). 각 행에 `사고 n건 · 신뢰도 Z%` 표기 → 0건 매장이 동료집단 평균으로 잡혔음을 라벨로 노출. 사망 보유 매장은 EAL을 사망 제외분으로 계산하고 우측에 회색 소자 `중대재해 1건`(정렬 미반영)

#### ⚠️ 기존 KPI와의 배율 차이 — 라벨로 구분한다

당초 "누적 손실과 EAL을 나란히 두면 서로를 설명한다"고 보았으나, 실측 결과 **두 수치가 2.25배 벌어진다.**

```
총 추정 재무손실   83.1억    ← 실측 근로손실일수만 (결측 미보정, 모수 646)
연간 기대손실      74.9억/년  ← 결측 보정 포함 · 사망 제외 (모수 620)
                  ×2.5년 = 187.2억
```

원인은 **결측 59%를 한쪽만 보정**하기 때문이다. 같은 탭에 설명 없이 놓으면 신뢰를 잃으므로, 두 KPI 부제에 산출 근거를 각각 명시한다(`실측분만` / `결측 보정 포함`). 결측률 자체는 원천 데이터 수집 과제이므로 본 설계에서 해결하지 않는다.

### ③ 조직 탭 (`DeptTeamStore.jsx`) — 컬럼 추가

부서·팀 테이블의 `매장 수 / 사고 수 / 매장당 사고율` 옆에 `연간 기대손실` 컬럼 추가.

### 표기 원칙

[[sago-no-estimate-badges]] 무배지 방침에 따라 **경고 배너·추정 배지를 넣지 않고 라벨로만** 전달한다. 모든 EAL 카드 부제에 `관측 2024-01~2026-06 · 2.5년 기준`처럼 **산출 근거 기간을 항상 명시**한다.

연도 필터 시 해당 연도만의 실측 빈도로 재계산된다. 2026년만 선택하면 6개월 실측을 연간 환산해 ×2가 되므로(통계적으론 옳으나 표본이 얇음), 관측 기간 노출로 사용자가 스스로 판단하게 한다.

## 8. 검증 — `scripts/validate-eal.mjs`

프로젝트에 프런트 테스트 인프라가 없어(별건 CI 과제), 기존 `validate-taxonomy.mjs` 패턴을 따라 검증 스크립트로 간다.

1. **가법성** — `Σ(유형×장소) == Σ(조직별) == 전사 총액` (오차 1원 미만). **모든 축이 동일하게 사망 제외 모수**임을 함께 확인한다.
2. **보정 정합** — 결측 보정 후 총 손실일수 = 관측치 + 보정분. 사망은 양쪽 어디에도 포함되지 않아야 한다.
3. **신뢰도 경계** — `Z ∈ [0,1]`, `n=0 → Z=0`, `n` 증가 시 단조증가
4. **매장 합계 괴리율** — 전사 대비 차이 리포트 (실패 아님, 의도된 결과)
5. **기간 계산** — 진행 중 당월이 분자·분모 양쪽에서 제외됐는지
6. **사망 판별 일관성** — `count(typeCanon==='사망') === count(kind==='사망')`. 두 필드가 갈리는 순간 `LegalReporting`의 CRITICAL 카운트와 EAL이 서로 다른 사망 건수를 말하게 되므로 감시한다.
7. **사망 미포함 확인** — 어떤 EAL 집계 결과에도 `isFatal` 레코드의 기여분이 0원인지 확인.

`npm run validate:eal`로 실행. `DAILY_VALUE_PER_WORKER` 변경 시 회귀 확인용으로도 사용.

### 9.2 사망 재해 처리 — **결정됨: 금액 축에서 분리** (2026-07-29)

#### 결정

**사망은 EAL(금액) 집계에서 제외하고, 건수 + 법정 요양근로손실일수로 별도 표기한다.**

#### 근거 1 — 7,500일은 손실액 기준이 아니다

「산업재해통계업무처리규정」(고용노동부예규 제190호) **별표1**은 사망의 요양근로손실일수를 7,500일로 규정하며, 이는 한국 **법정 수치가 맞다.** 다만 그 용도가 다르다.

| 용도 | 한국 공식 산식 | 사망 처리 |
|---|---|---|
| **강도율** (안전성과 지표) | 총요양근로손실일수 ÷ 연근로시간수 × 1,000 | **7,500일** (별표1 정액) |
| **경제적 손실액** (한국노동연구원·정부 발표) | 산재보험 급여 × 5 | **유족보상 1,300일분 + 장의비 120일분** |

즉 `7,500일 × 일급 × 5`는 **강도율용 정액치를 손실액 산식에 밀어넣는 범주 오류**다. 7,500일의 존재 목적 자체가 "사망은 실제 근로손실일수가 0으로 잡혀 심각도 지표에서 사라진다"를 막는 **가시성 장치**이지 금액 추정이 아니다.

> 참고: 국제 기준도 단일하지 않다. ILO(16차 ICLS, 1998)·일본·한국은 7,500일, **ANSI/ASSP Z16.1은 6,000일**, OSHA/BLS는 정액 환산을 쓰지 않고 사망을 CFOI로 완전 별도 집계한다.

#### 근거 2 — 이 레코드는 업무상 사망으로 확정되지 않았다

```
2025-11 · 인천영업부/일산팀 · 홈플러스강서점
kind='사망' type='사망' typeCanon='사망'
loss_days=null  dx=null  submitted=false  applyType=null  locLabel='장소불명'
content: 얼굴 피부트러블·허벅지 종기 → 병원 검사 → 결과 대기 중
```

산재 미신청·상병명 없음·발생장소 불명이며, 산재승인DB(`approvalData.totalApproved` 330건) 유형 분포에 `사망`이 **0건**이다. ILO 7,500일은 *work-related fatality* 전제의 환산이므로 적용 대상 자체가 아니다.

**부수 효과**: 이 레코드는 `liveSnapshot`에서 `approvalYn=""`이라 `liveSource.js:84`의 산재승인 필터를 통과하지 못한다. 금액에 포함시켰다면 기준 토글 한 번에 전사 EAL이 약 12억(13.8%) 점프했을 것이다. 분리하면 이 문제도 함께 사라진다.

#### 근거 3 — 랭킹이 이 기능의 목적을 배반한다

7,500일 적용 시 유형×장소 랭킹(실측):

```
1위  사망|장소불명   12.04억  (n=1)   ← 표본 1건 · 장소불명 · 개입점 없음
2위  넘어짐|계단     10.80억  (71건)
```

이 기능은 **"표본 5건짜리 조합이 실기여 1위를 밀어내는 문제"(§1)를 고치려고** 만든 것인데, 표본 1건짜리를 1위에 올리면 같은 병리를 더 심한 형태로 재현한다.

#### 근거 4 — 공시 관행이 분리를 요구한다

**GRI 403-9**는 사망자·중대재해·기록대상재해를 각각 보고하도록 요구하며, 고위험 재해 산정에서 *"exclude fatalities"*를 명시한다. 국내 유통사(롯데쇼핑·이마트) 공시에서도 사망을 다른 재해와 금액 합산한 사례가 확인되지 않았다.

#### 근거 5 — 기존 코드가 이미 분리 취급 중

| 위치 | 사망 취급 |
|---|---|
| `LegalReporting.jsx:103` | 사고사망(T10) 전용 KPI 타일 — 건수만, 금액 없음 |
| `LegalReporting.jsx:32` | 유일한 CRITICAL 알림 (CEO·안전보건총괄·법무팀) |
| `CostRisk.jsx:69` | `.filter(t => t.days > 0)` → 사망은 이미 비용 탭에 미등장 |
| `causeTaxonomy.js:171` | `classifyWorkerSubCause` 조기 return, 규칙 매칭 건너뜀 |

즉 분리는 새 관행이 아니라 **기존 관행으로의 복귀**다.

#### 구현 지침

1. `eal.js`에 술어를 한 곳에 둔다 — `isFatal(rec) = rec.typeCanon === '사망' || rec.kind === '사망'`. 두 필드를 모두 보는 이유는 `LegalReporting`이 `kind`를, EAL이 `typeCanon`을 쓰기 때문이며, 불일치는 §8-6이 감시한다.
2. **사망은 결측 보정(imputation) 대상에서 제외한다.** 현재 `typeMean['사망']`이 존재하지 않아 전사 평균 폴백을 타는 유일한 케이스이므로, 그 경로를 명시적으로 차단한다.
3. `metrics.js`에 `DEATH_LOSS_DAYS = 7500`을 두되 **금액 환산에 쓰지 않는다.** 별도 표기용 법정 수치다.
4. 화면 표기는 §5 참조.

#### 남는 한계

`type`·`cause`가 모두 '사망'으로 채워져 **원인 정보가 소실**됐다(넘어져 사망하면 입력자에 따라 '넘어짐' 또는 '사망'으로 갈린다). 또한 중대재해 후보 4건(지주막하뇌출혈 등)이 `질병`으로 코딩돼 있고 예후 데이터가 없어, 이 중 사망 확정 건이 있어도 현 판별로는 잡히지 않는다. 원천 데이터 품질 과제로 남긴다.
