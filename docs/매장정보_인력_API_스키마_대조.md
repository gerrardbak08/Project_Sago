## 0. 지금 확인된 것 — 코드가 이미 기대하는 필드명과 실제 데이터가 다르다

`processStores.js`는 다음 헤더를 기대하도록 이미 작성돼 있다(코드 주석 그대로):

> 매장코드 / 매장명 / 팀 / 부서 / 부문 / 형태 / 폐점여부 / 단품관리 / 오픈일 / 평수 / 실평수 / 창고 / 계약면적(㎡) / 진열평수 / 신주소 / 출고물류센터

그런데 현재 `raw/stores.json`(관리자 엑셀 업로드 경로, `SCHEMA_STORE` 기준)의 실제 키는 다음과 같다(1,337건 전수 확인):

```
매장, 매장명, 지역, 형태, 폐점여부, 구분, 오픈일, 평수, 실평수, 창고, 계약면적(㎡), 진열평수, 신주소
```

두 스키마를 나란히 놓으면:

| 코드가 기대하는 이름 | 현재 데이터의 실제 이름 | 결과 |
|---|---|---|
| `매장코드` | (없음, `매장`이 코드 역할 추정) | `code` 필드 사실상 비어 있음 |
| `팀` | `지역` (폴백 있음: `r["팀"] \|\| r["지역"]`) | ✅ 정상 동작 |
| `부서` | **(없음)** | `dept`가 항상 `undefined` — 사고DB의 팀명으로 역보완 중 |
| `부문` | **(없음)** | `bum`이 항상 `undefined` — 사고DB로 역보완 중 |
| `단품관리` | `구분`(값: 단품관리/금액관리) | `type`이 항상 `undefined` (키 이름 불일치) |
| `매장인원` | **(없음)** | `workers`가 항상 `null` — IR 분모가 사고DB 인력 폴백에 의존 |

**즉 지금 문제는 "API가 없어서 못 채우는 필드"가 아니라, 이미 두 벌의 다른 이름 규칙이 공존하고 있다는 것이다.** 매장정보 API 설계 시 아래 §1의 "요청 필드명"을 그대로 채택하면 이 불일치가 근본 해소된다.

## 1. 매장정보 API — 요청 필드

| 필드(요청명) | 타입 | 용도 | 현재 상태 |
|---|---|---|---|
| `매장코드` | string | 매장인력 API·향후 사고이력 API와의 **1차 조인 키**(현재는 이름 퍼지매칭에 의존) | ❌ 없음 |
| `매장명` | string | 대시보드 전체 조인 키 | ✅ 있음 |
| `부문` | string | "수도권"/"지방" | ❌ 없음 (사고DB로 역보완) |
| `부서` | string | 예: "인천영업부" | ❌ 없음 (사고DB로 역보완) |
| `팀` | string | 예: "강남팀" | ⚠️ `지역` 필드로 대체 수신 중 |
| `형태` | string | 직영점/유통점/유통행사 | ✅ 있음 |
| **`폐점여부`** | string | **계약값을 "폐점"/"영업중"/빈값=영업중으로 명시 요청.** 지금 코드(`processStores.js`)가 값 정의 문서(`schemas.js`)와 다른 값(`Y/TRUE/1/예`)을 검사하던 버그를 2026-08-31 수정했다(A1). 실제 API 값이 이 셋과 또 다르면 재확인 필요 | ✅ 수정 완료, **API 실값과 대조 필요** |
| `단품관리` | string | 재고관리 방식 — 현재 `구분` 필드로 대체 수신 중(키 이름만 다름, 값은 호환) | ⚠️ 키 이름 통일 요청 |
| `오픈일` | date | 매장 연차(`age`) 산출 | ✅ 있음 |
| `평수` / `창고` / `진열평수` | number | 규모·창고비율·진열비율 | ✅ 있음 |
| **`매장인원`** | number | Overview 인원 분모(현재 `1337×5` 하드코딩 추정치 대체), 규모별 평균인원(`size_stats`) | ❌ 없음 — 매장인력 API로 대체 가능하면 이 필드는 생략 가능(§3 참고) |
| `신주소` | string | 시군구 추출 + **위험지도 좌표 지오코딩 입력**(현재 좌표는 `storesData.js`에 수동 baked) | ✅ 있음 |

### 폐점 표기 관련 확인 요청

`processStores.js`는 폐점 매장을 제외한 뒤 집계한다. 현재 라이브 스냅샷 1,337건은 **전부 `"영업"`**이라 폐점 매장이 한 건도 없다 — 즉 이 필터가 지금까지 한 번도 "실제로 걸러본 적"이 없다. API 수신 시 폐점 매장이 섞여 오는지, 온다면 정확한 문자열 값이 무엇인지 확인 부탁드린다.

## 2. 매장인력 API — 요청 필드

기존 관리자 업로드 스키마(`SCHEMA_WORKER`, `processData.js`의 `processWorkers()`)가 이미 아래 필드로 동작 검증돼 있다. **같은 필드명이면 어댑터 작성만으로 연결된다.**

| 필드 | 타입 | 용도 | 비고 |
|---|---|---|---|
| `부문` | string | "수도권영업부문"/"지방영업부문" (본사 인원은 부문 없음으로 자동 구분) | 필수 |
| `부서` | string | | 필수 |
| `팀` | string | | 필수 |
| `조직명` | string | **매장명과 조인되는 키** — 매장정보 API의 `매장명`과 동일 값이어야 함 | 필수 |
| `직책` | string | "점장" 포함 여부로 관리자 판정. 현재 파트장 매핑(`parjangByStore.js`)이 **엑셀 수동 갱신**인데, 이 필드로 자동 생성 전환 가능 | 필수 |
| `사원상태` | string | "재직"만 카운트 — 재직/퇴사 값 정의 확인 요청 | 선택(없으면 전원 재직으로 간주될 위험 — **명시 요청**) |
| `입사일자` | date | 근속연수(`tenureYr`) → 신입 비율(1년/6개월 미만) | 선택 |

### 두 API 간 조인 키 공유 여부 — 가장 먼저 확인할 것

현재 매장DB↔인력DB 조인은 매장명 정규화 + **편집거리(Levenshtein) ≤2 퍼지매칭**으로 이뤄진다(오매칭 위험 상시 존재, `worker_join` 진단으로 관리 중). 두 API가 **같은 매장코드 체계**를 쓴다면 이 퍼지매칭을 코드 조인으로 대체해 위험을 없앨 수 있다. **IT에 반드시 확인**: 매장정보 API의 매장코드와 매장인력 API의 조직 코드가 동일한 채번 규칙인가?

## 3. 두 API가 함께 도착했을 때 자동으로 좋아지는 것

| 화면/지표 | 현재 상태 | API 반영 후 |
|---|---|---|
| 부서·부문별 IR(100인당 재해율) | 인력 데이터가 없어 정적 5월 스냅샷 고정(`App.jsx`의 `STATIC_KEEP`) | 매장·팀 단위까지 상시 라이브 갱신 |
| 위험지도(StoreRiskMap) | 좌표가 `storesData.js`에 수동 baked, 신규 매장 미표시 | 신주소 → 지오코딩 자동화로 신규 매장 즉시 반영 |
| EAL Top20·반복사고 매장 | 매장 마스터 미매칭 시(현재 약 1%) 누락 | 매장코드 조인으로 미매칭률 축소 |
| Overview 인원 분모 | `1337×5`(매장수×추정 평균인원) 하드코딩 | 매장인력 API 실측 합계로 대체 |
| 파트장 매핑 | 별도 엑셀(`update-parjang-by-store.mjs`) 수동 갱신 | 인력 API `직책=점장` 필드로 자동 생성 |

**주의 — 어댑터만으로는 화면에 반영되지 않는다.** `App.jsx`의 `STATIC_KEEP` 집합(`worker_ir_summary`, `team_ir`, `dept_ir`, `size_stats` 등)이 라이브 값을 무시하고 정적 5월 스냅샷을 강제하고 있다. 인력 API 연결 시 이 집합에서 IR 관련 키를 제거하는 작업이 **반드시 짝으로** 진행돼야 한다(성별·상병 등 인적속성 필드는 계속 정적 유지 — 인력 API에 없을 가능성이 높음).

## 4. 전환 시 체크리스트

- [ ] 매장정보 API — `매장코드` 필드 존재 여부 및 값 예시
- [ ] 매장정보 API — `부문`/`부서`/`팀`(또는 `지역`) 필드명 확정
- [ ] 매장정보 API — `폐점여부` 실제 값 문자열 확인(`"폐점"`/`"영업중"`/다른 값?)
- [ ] 매장정보 API — `매장인원` 포함 여부(포함 시 매장인력 API와 중복 소스가 되므로 우선순위 합의)
- [ ] 매장인력 API — `조직명`(매장명)이 매장정보 API의 매장명과 **문자열까지 동일**한지 샘플 대조
- [ ] 매장인력 API — `사원상태` 값 정의(재직/퇴사 외 다른 상태 존재 여부)
- [ ] 두 API — **매장코드 채번 규칙 공유 여부** (§2 참조, 가장 중요)
- [ ] 수신 방식 — 이 프로젝트는 빌드타임 baked 정적 스냅샷 원칙(`liveSnapshot.js` 패턴)을 쓴다. 런타임 fetch가 아니라 **주기적 재베이크**(예: `data:stores`, `data:workers` npm 스크립트) 방식으로 설계 요청
